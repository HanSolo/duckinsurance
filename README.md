# DuckInsurance

A small, PetClinic-style reference application for **Jakarta EE 11**, built around an insurance domain
(duck owners, ducks, vets, policies, claims), matching the Duck-Clinic scheme. It targets **Payara 7** by default; the code only uses standard APIs
(plus one `glassfish-web.xml` for context root and role mapping), so other EE 11 runtimes should work too.

## Run it

```bash
docker compose up --build        # builds the WAR and starts Payara 7
# or, without Docker (JDK 21+, Maven, Payara Micro 7 jar):
mvn package
java -jar payara-micro.jar --deploy target/duckinsurance.war
```

Open <http://localhost:8081> and sign in:

| User       | Password   | Role     | Can do                                   |
|------------|------------|----------|------------------------------------------|
| `admin`    | `admin`    | ADMIN    | everything                               |
| `adjuster` | `adjuster` | ADJUSTER | view, submit claims, approve / reject    |
| `customer` | `customer` | CUSTOMER | view, submit claims                      |

Data lives in the server's default H2 datasource and is re-created (with seed data) on every start.

## Feature map: where do I see X?

| Specification        | Where                                   | What it shows |
|----------------------|-----------------------------------------|---------------|
| Persistence 3.2      | `domain/`, `META-INF/persistence.xml`   | entities, `java.time`, schema generation |
| Data 1.0             | `repo/`                                 | `@Repository`, `@Find`, `@Query` (JDQL), `countBy…` |
| REST 4.0             | `rest/`                                 | JSON-B, record request bodies, `@RolesAllowed`, exception mapper |
| CDI 4.1              | `event/`, `audit/`, `config/DataSeeder` | `Startup` event, sync + async events, `AFTER_SUCCESS` observer, interceptor binding |
| Concurrency 3.1      | `config/ConcurrencyConfig`, `event/FraudCheck`, `config/PolicyMaintenance` | virtual-thread executor, `@Asynchronous(runAt = @Schedule)` |
| Transactions 2.0     | `service/`                              | `@Transactional` services |
| Security 4.0         | `security/`                             | `HttpAuthenticationMechanism` (session for Faces, Basic for REST), `IdentityStore` |
| Agentic AI 1.0 (draft) | `agent/`                              | `@Agent`, `@Trigger`, `@Action`, `@Decision`, `@Outcome`, `@HandleException`, injected `LargeLanguageModel` |
| Validation 3.1       | `domain/`, `rest/Requests`              | constraints on entities and records |
| Faces 4.1            | `src/main/webapp/`                      | Facelets template, view-scoped beans, `f:ajax`, `viewParam` |

Try this flow: sign in as `customer`, submit a claim, watch the **fraud risk** go from "checking…" to a score
(a virtual thread started after the transaction committed), then sign in as `adjuster` and approve it.
The dashboard's activity log shows the interceptor and the asynchronous notification.

A 15-minute walkthrough with a story is in [DEMO.md](DEMO.md).

## REST API

All endpoints under `/api`, HTTP Basic or session cookie. The OpenAPI description (MicroProfile OpenAPI annotations, generated by Payara) is at `/openapi`; the sidebar links to it.
An editor such as Swagger UI or Postman can import that URL. Use HTTP Basic with `admin`, `adjuster` or `customer`.


```bash
curl -u admin:admin http://localhost:8081/api/customers
curl -u admin:admin http://localhost:8081/api/policies/quote -H 'Content-Type: application/json' \
     -d '{"duckId":1,"type":"VET_CARE","coverageAmount":5000}'
curl -u customer:customer http://localhost:8081/api/claims -H 'Content-Type: application/json' \
     -d '{"policyId":1,"vetId":1,"description":"Sir Quacksalot swallowed a bread bag clip","amount":600,"incidentDate":"2026-10-01"}'
curl -u adjuster:adjuster http://localhost:8081/api/claims/3/decision -H 'Content-Type: application/json' \
     -d '{"approve":true,"note":"ok"}'
```

Resources: `customers` (the owners), `customers/{id}/ducks`, `customers/{id}/policies`, `ducks`, `vets`, `policies`, `policies/quote`, `policies/{id}/cancel`,
`claims`, `claims/{id}/decision`, `stats`.

## Design choices (and known simplifications)

- One WAR, layered packages instead of microservices: easier to present, services are still separate CDI beans.
- Policies and claims reference their parent by plain id instead of JPA relationships, to keep JSON and Faces simple.
- Demo accounts and plain-text passwords are for demonstration only.
- Not yet verified against a running server: this project was written without being able to build or deploy it.
  Expect to fix small things on the first run.

## MCP: let an LLM use the app

The WAR contains the [Jakarta MCP server](https://github.com/HanSolo/jakarta-mcp-server) library (`eu.hansolo.mcp:mcp-jakarta:1.1.0`).
`mcp/DuckTools` turns the CDI services into 10 tools (`search_owners`, `list_ducks`, `list_vets`, `list_policies`, `quote_policy`,
`issue_policy`, `list_claims`, `submit_claim`, `decide_claim`, `get_stats`). The endpoint is `http://localhost:8081/api/mcp` and uses the
application's own login (HTTP Basic), so roles apply: `customer` cannot decide claims, `adjuster` and `admin` can.

The server speaks only MCP revision **2026-07-28** (no `initialize` handshake). Clients that still need the handshake are refused with HTTP 400.

### The Assistant page (MCP client inside the app)

The sidebar entry **Assistant** is a chat page. It uses the [Jakarta MCP client](https://github.com/HanSolo/jakarta-mcp-client) (`eu.hansolo.mcp:mcp-jakarta-client:0.3.0` from Maven Central) to read the tools from `/api/mcp` and runs a tool-calling loop (`chat/AgentLoop`) against a model. The client sends a short-lived signed token (`security/InternalTokens`, HMAC, 2 minutes, accepted by `AppAuthMechanism` as a Bearer token) for the logged-in user,
so the assistant acts with that user's role. The model defaults to an Ollama on the host (`http://host.docker.internal:11434`, model `qwen3.8:27b`); Ollama speaks the Anthropic Messages API since 0.14. On Linux, Ollama must listen on more than loopback for the container to reach it (`OLLAMA_HOST=0.0.0.0`); Docker Desktop needs nothing. Claude or an OpenAI-format service work too, see "Using a cloud model".
Settings: see **Configuring the model** below (`llm.env`).
`MCP_SELF_URL` overrides the endpoint the page calls (default `http://localhost:8080/api/mcp`).

**Streaming:** the answer is requested with `stream: true` (server-sent events) and appears while the model writes. The question runs on a background thread, the page polls every 600 ms. A Stop button cancels the run.
Needs Ollama 0.14 or newer (`ollama --version`).

**Confirmation:** `issue_policy`, `submit_claim` and `decide_claim` do not act on the first call. They answer with an MCP elicitation (multi round-trip request) and a signed `requestState` that contains the exact arguments.
The Assistant page shows a "Please confirm" card; only after *Yes* is the call repeated and executed. Declining returns "Nothing was changed". Environment variable `DUCK_CONFIRM_WRITES`:
`if-supported` (default: ask when the client can be asked, act directly for clients without elicitation such as simple scripts), `always` (refuse clients that cannot ask), `off`.

### From a terminal, with a local model (Ollama, no internet after the model download)

```bash
docker compose up --build -d
node scripts/duckchat.mjs                            # Node 20+, interactive, as user "customer"; OLLAMA_MODEL=... to change the model
MCP_USER=adjuster node scripts/duckchat.mjs "Approve the open claim of Don Quixote"
```

`scripts/duckchat.mjs` is a small bridge: it reads the tool list over MCP, hands it to Ollama's `/api/chat`, runs the tool calls the model asks for and feeds the results back.
If Ollama runs on the host instead of in Docker, nothing changes (default `http://localhost:11434`).

## Fraud agent (Jakarta Agentic AI, draft)

Vet-care and physiotherapy claims are checked against the **DuckClinic** and the **Duck Physical Therapy Clinic** by an agent written to the draft [Jakarta Agentic AI 1.0 (milestone 1)](https://jakarta.ee/specifications/agentic-ai/1.0/) model: `agent/ClaimFraudAgent` is a CDI bean annotated `@Agent`.
New claims first get the quick rule-based check. The agent runs per claim, when you press **Check** in the claims list (`agent/AgentCheck`, in the background; press Refresh afterwards). A CDI event (`ClaimCheckRequest`) starts the workflow: `@Trigger` -> `@Action` (reads the duck's visits from the clinic's MCP server through `agent/ClinicClient`, the MCP client library)
-> `@Decision` (the language model, injected as `LargeLanguageModel`, compares claim and visits and answers with a score and a reason) -> `@Outcome` (stores both on the claim and moves it to review).
`@HandleException` notes a failure on the claim, which keeps its rule-based score. The Check button only appears for open vet-care claims; other claim types always use the rule-based check.

- The **Duck Physical Therapy Clinic** (a Quarkus application, MCP endpoint `PHYSIOCLINIC_MCP_URL`, default `http://host.docker.internal:8082/mcp`) is asked the same way (`agent/PhysioClient`). Its tools: `list_ducks`, `list_appointments_for_duck`, `list_treatments`, `list_therapists`, `book_appointment`. Ducks are matched by name and the owner's last name. Physiotherapy policies (`PHYSIO`) are new; their claims are checked like vet-care claims.
- If neither clinic has a record of the treatment near the incident date, the duck is known to the physical therapy clinic and the claim is about therapy, the agent stores a **proposal** on the claim: a treatment, a therapist (chosen by the model from the clinic's lists) and the next working day at 10:00. Adjusters and admins see it under the score and press **Book it**; only then is `book_appointment` called. The agent itself never writes to the clinic. The clinic checks availability at that moment, so a booking can still be refused.
- A clinic that cannot be reached is treated as unknown, not suspicious. Only if neither can be reached, the claim gets the rule-based check, unless the claim blames the weather and the public weather server answers: then the agent runs with the weather only (see "Weather check"). So the Ducky McDuckface demo works with DuckInsurance alone.
- The **Claims** page has one indicator per clinic, like the assistant's: green when the DuckClinic MCP endpoint is reachable and offers `find_owners` and `list_visits`. The reason of the agent is shown under the fraud score.
- Needs **Payara 7.2026.8 or newer** (the image uses 7.2026.10), which ships the first preview of the API. The API may still change.
- Settings: `DUCKCLINIC_MCP_URL` (default `http://host.docker.internal:8080/duck-clinic/api/mcp`), `DUCK_FRAUD_AGENT=off` to start with the agent switched off (see "Demo switches"), `DUCK_FRAUD_INVESTIGATE=off` to skip the agent's investigation round.
- The clinic uses host port 8080, so DuckInsurance is published on **8081** (`DUCKINSURANCE_PORT` in `.env`, default 8081). The container itself still listens on 8080, which is why `MCP_SELF_URL` keeps its default. To move the clinic instead, set `DUCKINSURANCE_PORT=8080` and `DUCKCLINIC_MCP_URL`.
- Demo data: copy `duck-clinic-patch/DataInitializer.java` into the clinic (see `duck-clinic-patch/README.md`), so the insured ducks exist there.
- **Which model answers:** the agent injects the standard `LargeLanguageModel`. The application supplies that bean itself (`agent/ConfiguredLlm`), which reads `LLM_PROVIDER`, `LLM_BASE_URL`, `LLM_MODEL`, `LLM_API_KEY` and `LLM_MAX_TOKENS` from `llm.env` through MicroProfile Config. See "Using a cloud model".
  The reason shown under the fraud score starts with `[agentic-ai]`. `[rules]` means the model answered but not in the expected JSON format, so a fixed rule judged instead. If the model or the clinic cannot be reached, the claim keeps its rule-based score and the reason says that the agent failed.
- **Pattern signals and investigation:** before the model is asked, `agent/PatternSignals` looks for patterns across all claims in code, because a language model is unreliable at counting and comparing records: `SAME_WORDING` (another claim with almost the same description), `DUPLICATE_INVOICE` and `SPLIT_INVOICE` (another claim for the same duck within 7 days, with almost the same amount or a different one), `PRIOR_REJECTION` (the owner has a rejected claim), `REPEAT_DUCK` and `REPEAT_OWNER` (other claims within 90 days, for the same duck or another duck of the owner), `EARLY_CLAIM` (incident less than 30 days after the policy started), `NEAR_LIMIT` (amount at least 90% of the coverage) and `HIGH_AMOUNT` (at least twice the median of the other claims of that policy type). The signals are facts, not verdicts: the prompt tells the model that a matching clinic record outweighs a repeat claim, unless the same invoice may have been claimed twice.
  If more evidence could change its score, the model may name up to three checks from a fixed list in the `investigate` field of its JSON answer: `OWNER_CLAIMS`, `SIMILAR_CLAIMS`, `OWNER_POLICIES`, `OWNER_OTHER_DUCKS` (visits of the owner's other ducks at the DuckClinic), `SAME_VET_CLAIMS`. `agent/FraudInvestigation` runs them in code, read only, and the model answers once more with the evidence. Unknown names are ignored. This needs no tool-calling support from the model, so it works the same with Ollama, Claude and OpenAI-format services (Groq included). If the second call fails (for example a rate limit longer than 30 seconds), the first answer counts and the details say so.
  In the claim list the check result is collapsed to one line with "n signals · n checks"; clicking it opens the full reason, the signals and what each check found (`agent/FraudTrail`, in memory only: after a restart a claim shows its stored reason, and Check fills the details again). The steps are also in the log of the **Agents** page under the claim number. All of it follows the **Fraud** demo switch. `DUCK_FRAUD_INVESTIGATE=off` keeps the signals but skips the second round. The agent timeout is 240 seconds because of the second model call.
- **Weather check (a public MCP server on the internet):** if a claim blames the weather (hail, thunderstorm, storm, heavy rain or flood, frost or snow, heat), the fraud agent asks a **public weather MCP server** what the weather really was in the owner's town from the day before to the day after the incident. Here DuckInsurance is the MCP *client* of a server that somebody else runs; the clinics show the other direction. Default server: the free, keyless [Open-Meteo MCP server](https://github.com/cyanheads/open-meteo-mcp-server) at `https://open-meteo.caseyjhand.com/mcp` (tools `openmeteo_search_locations` and `openmeteo_get_historical`; weather data by [Open-Meteo.com](https://open-meteo.com), CC BY 4.0, free for non-commercial use).
  `WEATHER` is a sixth check on the fixed list. When the description names a weather event, the code adds the signal `WEATHER_EVENT`, and if the model does not ask for `WEATHER` itself, the insurer's rule adds it (the log says so). The code reads the numbers (a hail claim needs a thunderstorm, weather code 95 to 99; a storm needs gusts of about 75 km/h; heavy rain about 20 mm a day; frost 0 °C or snow; heat 30 °C) and gives the model the days plus that reading. Answers are cached in memory per town and date. Files: `agent/WeatherClient`, `agent/WeatherCheck`, `agent/WeatherUnavailableException`, `agent/FraudInvestigation`, `agent/ClaimFraudAgent`.
  **If the server cannot be reached**, the check says the weather is unknown and the model is told not to hold that against the claim; the claim is judged with everything else. The **Claims** page has a third indicator, "Weather (public MCP server on the internet)": green when the server answers and offers both tools, red when not, yellow when switched off. Settings: `WEATHER_MCP_URL` (another endpoint, for example a self-hosted copy of the same open-source server) or `WEATHER_MCP_URL=off` (no check, no signal, not on the menu).
  Demo data: **Ducky McDuckface** (Lena Fischer, Vienna) claims hail injuries 12 days ago. Hail needs a thunderstorm, which is rare in Vienna (almost never outside summer), so on nearly every demo day the weather contradicts the claim. On a day after a real thunderstorm in Vienna the agent will correctly say hail was plausible.
- **What does not use the spec:** the Assistant page (streaming, tool calls and confirmations are outside the draft API, it uses its own client) and the reading of the clinic (MCP client library).

## Demo switches

To tell the story step by step (a plain Jakarta EE application first, then the Assistant, then the fraud agent, then the agent-to-agent part),
an `admin` sees three small switches at the bottom of the sidebar: **AI** (Assistant page), **Fraud** (fraud agent) and **A2A** (Agents page).
They apply to every user at once and need no restart. Switched off:

- **AI:** the menu entry is hidden and the page sends the browser to the dashboard.
- **Fraud:** the agent status, the Check button and the Agentic AI badge on the Claims page are hidden; claims get only the rule-based score. A claim the therapy clinic files still gets the rule-based score.
- **A2A:** the menu entry is hidden and the page sends the browser to the dashboard. The partner tools for the clinics' agents keep working.

Start values: `DUCK_ASSISTANT`, `DUCK_FRAUD_AGENT`, `DUCK_AGENTS_TAB` (`on` or `off`, default `on`). A restart goes back to them (`web/DemoFeatures`).

## Configuring the model (`llm.env`)

The model settings are not in the code. `llm.env` (next to `compose.yaml`, template: `llm.env.example`) is loaded by Docker Compose into the container's environment (`env_file`), at every start.
Edit it and run `docker compose up -d`; no rebuild is needed. The application reads its settings with **MicroProfile Config** (`config/AppConfig`), the usual way for Jakarta EE applications: sources are system properties (`-D`), environment variables, and `META-INF/microprofile-config.properties`.
That also works without Docker: set the same names as environment variables or `-D` properties on the server. `llm.env` is in `.gitignore` because it can hold an API key.

| Variable | Meaning | Default |
|---|---|---|
| `LLM_PROVIDER` | provider of the agents: `ollama`, `anthropic` (alias `claude`) or `openai` | `ollama` |
| `LLM_BASE_URL` | model server, used by the Assistant and the agents | Ollama on the host |
| `LLM_MODEL` | model name, used by the Assistant and the agents | `qwen3.8:27b` |
| `LLM_API_KEY` | key, used by the Assistant and the agents; any text for Ollama | `ollama` |
| `LLM_MAX_TOKENS` | answer length (anthropic: 4096; openai: none unless set) | |
| `ASSISTANT_PROVIDER`, `ASSISTANT_BASE_URL`, `ASSISTANT_MODEL`, `ASSISTANT_API_KEY` | optional: a different model for the Assistant only | |
| `ANTHROPIC_MAX_TOKENS`, `AGENT_MAX_ROUNDS` | optional limits of the Assistant | 1024, 8 |
| `DUCKCLINIC_MCP_URL`, `DUCK_CONFIRM_WRITES`, `MCP_SELF_URL` | see `compose.yaml` | |
| `DUCK_ASSISTANT`, `DUCK_FRAUD_AGENT`, `DUCK_AGENTS_TAB` | start value of the demo switches, `on` or `off` | `on` |

The older `ANTHROPIC_BASE_URL`, `ANTHROPIC_API_KEY` and `ANTHROPIC_MODEL` still work for the Assistant.

### Using a cloud model
Pick a provider in `llm.env` and run `docker compose up -d`:

| | `LLM_PROVIDER` | `LLM_BASE_URL` | `LLM_MODEL` | `LLM_API_KEY` |
|---|---|---|---|---|
| Local Ollama (default) | `ollama` | `http://host.docker.internal:11434` | `qwen3.8:27b` | any text |
| Claude | `anthropic` | `https://api.anthropic.com` | a Claude model name | Anthropic key |
| OpenAI format (OpenAI, Groq, OpenRouter, Mistral, ...) | `openai` | the service's URL with `/v1`, e.g. `https://api.openai.com/v1` | that service's model name | that service's key |

- **Fraud and pre-authorization agents:** they inject `LargeLanguageModel` as before, but the bean now comes from the application (`agent/ConfiguredLlm`). Payara 7.2026.10 only has ollama, anthropic and vertex backends (read from `LlmBackendFactory` in `glassfish/modules/agentic-ai-core.jar`), no OpenAI format. When an application has its own managed bean of type `LargeLanguageModel`, Payara's `AgenticAIExtension` does not create its default, so `payara.agentic.llm.*` no longer applies.
- **Assistant:** uses the same `LLM_*` values. With `ollama` and `anthropic` it uses `chat/AnthropicLlm` (Ollama 0.14+ speaks the Messages API); with `openai` it uses `chat/OpenAiLlm`, which translates tools, tool calls and tool results to the Chat Completions format, streaming included. How well the Assistant uses tools depends on the model: some models on OpenAI-format services do not support tools at all, and small local models often stop after one step. `ASSISTANT_PROVIDER`, `ASSISTANT_BASE_URL`, `ASSISTANT_MODEL` and `ASSISTANT_API_KEY` optionally give the Assistant a different model than the agents.
- **`LLM_MAX_TOKENS`:** with `anthropic` the default is 4096 (thinking models such as qwen3 on Ollama spend part of it before they answer); with `openai` no limit is sent unless it is set, because newer OpenAI models reject `max_tokens` (Groq, OpenRouter and Mistral accept it).
- Never put a real key in `llm.env.example` or in the image.
