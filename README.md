# DuckInsurance

A small, PetClinic-style reference application for **Jakarta EE 11**, built around an insurance domain
(duck owners, ducks, vets, policies, claims), matching the Duck-Clinic scheme. It targets **Payara 7** by default; the code only uses standard APIs
(plus one `glassfish-web.xml` for context root and role mapping), so other EE 11 runtimes should work too.

## Run it

```bash
docker compose up --build        # builds the WAR and starts Payara 7
# or, without Docker (JDK 21+, Maven, Payara Micro 7 jar):
mvn package
java -jar payara-micro.jar --deploy target/duckinsurance.war
```

Open <http://localhost:8081> and sign in:

| User       | Password   | Role     | Can do                                   |
|------------|------------|----------|------------------------------------------|
| `admin`    | `admin`    | ADMIN    | everything                               |
| `adjuster` | `adjuster` | ADJUSTER | view, submit claims, approve / reject    |
| `customer` | `customer` | CUSTOMER | view, submit claims                      |

Data lives in the server's default H2 datasource and is re-created (with seed data) on every start.

## Feature map: where do I see X?

| Specification        | Where                                   | What it shows |
|----------------------|-----------------------------------------|---------------|
| Persistence 3.2      | `domain/`, `META-INF/persistence.xml`   | entities, `java.time`, schema generation |
| Data 1.0             | `repo/`                                 | `@Repository`, `@Find`, `@Query` (JDQL), `countBy…` |
| REST 4.0             | `rest/`                                 | JSON-B, record request bodies, `@RolesAllowed`, exception mapper |
| CDI 4.1              | `event/`, `audit/`, `config/DataSeeder` | `Startup` event, sync + async events, `AFTER_SUCCESS` observer, interceptor binding |
| Concurrency 3.1      | `config/ConcurrencyConfig`, `event/FraudCheck`, `config/PolicyMaintenance` | virtual-thread executor, `@Asynchronous(runAt = @Schedule)` |
| Transactions 2.0     | `service/`                              | `@Transactional` services |
| Security 4.0         | `security/`                             | `HttpAuthenticationMechanism` (session for Faces, Basic for REST), `IdentityStore` |
| Agentic AI 1.0 (draft) | `agent/`                              | `@Agent`, `@Trigger`, `@Action`, `@Decision`, `@Outcome`, `@HandleException`, injected `LargeLanguageModel` |
| Validation 3.1       | `domain/`, `rest/Requests`              | constraints on entities and records |
| Faces 4.1            | `src/main/webapp/`                      | Facelets template, view-scoped beans, `f:ajax`, `viewParam` |

Try this flow: sign in as `customer`, submit a claim, watch the **fraud risk** go from "checking…" to a score
(a virtual thread started after the transaction committed), then sign in as `adjuster` and approve it.
The dashboard's activity log shows the interceptor and the asynchronous notification.

A 15-minute walkthrough with a story is in [DEMO.md](DEMO.md).

## REST API

All endpoints under `/api`, HTTP Basic or session cookie. The OpenAPI description (MicroProfile OpenAPI annotations, generated by Payara) is at `/openapi`; the sidebar links to it.
An editor such as Swagger UI or Postman can import that URL. Use HTTP Basic with `admin`, `adjuster` or `customer`.


```bash
curl -u admin:admin http://localhost:8081/api/customers
curl -u admin:admin http://localhost:8081/api/policies/quote -H 'Content-Type: application/json' \
     -d '{"duckId":1,"type":"VET_CARE","coverageAmount":5000}'
curl -u customer:customer http://localhost:8081/api/claims -H 'Content-Type: application/json' \
     -d '{"policyId":1,"vetId":1,"description":"Sir Quacksalot swallowed a bread bag clip","amount":600,"incidentDate":"2026-10-01"}'
curl -u adjuster:adjuster http://localhost:8081/api/claims/3/decision -H 'Content-Type: application/json' \
     -d '{"approve":true,"note":"ok"}'
```

Resources: `customers` (the owners), `customers/{id}/ducks`, `customers/{id}/policies`, `ducks`, `vets`, `policies`, `policies/quote`, `policies/{id}/cancel`,
`claims`, `claims/{id}/decision`, `stats`.

## Design choices (and known simplifications)

- One WAR, layered packages instead of microservices: easier to present, services are still separate CDI beans.
- Policies and claims reference their parent by plain id instead of JPA relationships, to keep JSON and Faces simple.
- Demo accounts and plain-text passwords are for demonstration only.
- Not yet verified against a running server: this project was written without being able to build or deploy it.
  Expect to fix small things on the first run.

## MCP: let an LLM use the app

The WAR contains the [Jakarta MCP server](https://github.com/HanSolo/jakarta-mcp-server) library (`eu.hansolo.mcp:mcp-jakarta:0.9.0`).
`mcp/DuckTools` turns the CDI services into 10 tools (`search_owners`, `list_ducks`, `list_vets`, `list_policies`, `quote_policy`,
`issue_policy`, `list_claims`, `submit_claim`, `decide_claim`, `get_stats`). The endpoint is `http://localhost:8081/api/mcp` and uses the
application's own login (HTTP Basic), so roles apply: `customer` cannot decide claims, `adjuster` and `admin` can.

The server speaks only MCP revision **2026-07-28** (no `initialize` handshake). Clients that still need the handshake are refused with HTTP 400.

### The Assistant page (MCP client inside the app)

The sidebar entry **Assistant** is a chat page. It uses the [Jakarta MCP client](https://github.com/HanSolo/jakarta-mcp-client) (vendored in `third-party/`, because 0.1.0 is not on Maven Central yet;
the Dockerfile installs it before the build) to read the tools from `/api/mcp` and runs a tool-calling loop (`chat/AgentLoop`) against a model. The client sends a short-lived signed token (`security/InternalTokens`, HMAC, 2 minutes, accepted by `AppAuthMechanism` as a Bearer token) for the logged-in user,
so the assistant acts with that user's role. The model defaults to an Ollama on the host (`http://host.docker.internal:11434`, model `qwen3.8:27b`); Ollama speaks the Anthropic Messages API since 0.14. On Linux, Ollama must listen on more than loopback for the container to reach it (`OLLAMA_HOST=0.0.0.0`); Docker Desktop needs nothing.
Settings: see **Configuring the model** below (`llm.env`).
`MCP_SELF_URL` overrides the endpoint the page calls (default `http://localhost:8080/api/mcp`).

**Streaming:** the answer is requested with `stream: true` (server-sent events) and appears while the model writes. The question runs on a background thread, the page polls every 600 ms. A Stop button cancels the run.
Needs Ollama 0.14 or newer (`ollama --version`).

**Confirmation:** `issue_policy`, `submit_claim` and `decide_claim` do not act on the first call. They answer with an MCP elicitation (multi round-trip request) and a signed `requestState` that contains the exact arguments.
The Assistant page shows a "Please confirm" card; only after *Yes* is the call repeated and executed. Declining returns "Nothing was changed". Environment variable `DUCK_CONFIRM_WRITES`:
`if-supported` (default: ask when the client can be asked, act directly for clients without elicitation such as simple scripts), `always` (refuse clients that cannot ask), `off`.

### From a terminal, with a local model (Ollama, no internet after the model download)

```bash
docker compose up --build -d
node scripts/duckchat.mjs                            # Node 20+, interactive, as user "customer"; OLLAMA_MODEL=... to change the model
MCP_USER=adjuster node scripts/duckchat.mjs "Approve the open claim of Don Quixote"
```

`scripts/duckchat.mjs` is a small bridge: it reads the tool list over MCP, hands it to Ollama's `/api/chat`, runs the tool calls the model asks for and feeds the results back.
If Ollama runs on the host instead of in Docker, nothing changes (default `http://localhost:11434`).

## Fraud agent (Jakarta Agentic AI, draft)

Vet-care claims are checked against the **DuckClinic** by an agent written to the draft [Jakarta Agentic AI 1.0 (milestone 1)](https://jakarta.ee/specifications/agentic-ai/1.0/) model: `agent/ClaimFraudAgent` is a CDI bean annotated `@Agent`.
New claims first get the quick rule-based check. The agent runs per claim, when you press **Check** in the claims list (`agent/AgentCheck`, in the background; press Refresh afterwards). A CDI event (`ClaimCheckRequest`) starts the workflow: `@Trigger` -> `@Action` (reads the duck's visits from the clinic's MCP server through `agent/ClinicClient`, the MCP client library)
-> `@Decision` (the language model, injected as `LargeLanguageModel`, compares claim and visits and answers with a score and a reason) -> `@Outcome` (stores both on the claim and moves it to review).
`@HandleException` notes a failure on the claim, which keeps its rule-based score. The Check button only appears for open vet-care claims; other claim types always use the rule-based check.

- The **Claims** page has an indicator like the assistant's: green when the DuckClinic MCP endpoint is reachable and offers `find_owners` and `list_visits`. The reason of the agent is shown under the fraud score.
- Needs **Payara 7.2026.8 or newer** (the image uses 7.2026.10), which ships the first preview of the API. The API may still change.
- Settings: `DUCKCLINIC_MCP_URL` (default `http://host.docker.internal:8080/duck-clinic/api/mcp`), `DUCK_FRAUD_AGENT=off` to switch the agent off.
- The clinic uses host port 8080, so DuckInsurance is published on **8081** (`DUCKINSURANCE_PORT` in `.env`, default 8081). The container itself still listens on 8080, which is why `MCP_SELF_URL` keeps its default. To move the clinic instead, set `DUCKINSURANCE_PORT=8080` and `DUCKCLINIC_MCP_URL`.
- Demo data: copy `duck-clinic-patch/DataInitializer.java` into the clinic (see `duck-clinic-patch/README.md`), so the insured ducks exist there.
- **Which model answers:** the agent injects the standard `LargeLanguageModel`. Payara reads its settings through MicroProfile Config: `payara.agentic.llm.provider`, `.model` and `.ollama.base-url`, given as the environment variables the file `META-INF/microprofile-config.properties` fills them from the `LLM_PROVIDER`, `LLM_MODEL` and `LLM_BASE_URL` of `llm.env` (MicroProfile Config property expressions, `${LLM_MODEL:default}`). The key names come from a third-party demo of the Payara source (tag 7.2026.9) and are not in Payara's documentation.
  The reason shown under the fraud score starts with `[agentic-ai]`. `[rules]` means the model answered but not in the expected JSON format, so a fixed rule judged instead. If the model or the clinic cannot be reached, the claim keeps its rule-based score and the reason says that the agent failed.
- **What does not use the spec:** the Assistant page (streaming, tool calls and confirmations are outside the draft API, it uses its own client) and the reading of the clinic (MCP client library).

## Configuring the model (`llm.env`)

The model settings are not in the code. `llm.env` (next to `compose.yaml`, template: `llm.env.example`) is loaded by Docker Compose into the container's environment (`env_file`), at every start.
Edit it and run `docker compose up -d`; no rebuild is needed. The application reads its settings with **MicroProfile Config** (`config/AppConfig`), the usual way for Jakarta EE applications: sources are system properties (`-D`), environment variables, and `META-INF/microprofile-config.properties`.
That also works without Docker: set the same names as environment variables or `-D` properties on the server. `llm.env` is in `.gitignore` because it can hold an API key.

| Variable | Meaning | Default |
|---|---|---|
| `LLM_BASE_URL` | model server, used by the Assistant and the fraud agent | Ollama on the host |
| `LLM_MODEL` | model name, used by both | `qwen3.8:27b` |
| `LLM_API_KEY` | key, Assistant only (any text for Ollama) | `ollama` |
| `LLM_PROVIDER` | provider of the fraud agent's `LargeLanguageModel` | `ollama` |
| `ANTHROPIC_MAX_TOKENS`, `AGENT_MAX_ROUNDS` | optional limits of the Assistant | 1024, 8 |
| `DUCKCLINIC_MCP_URL`, `DUCK_FRAUD_AGENT`, `DUCK_CONFIRM_WRITES`, `MCP_SELF_URL` | see `compose.yaml` | |

The older `ANTHROPIC_BASE_URL`, `ANTHROPIC_API_KEY` and `ANTHROPIC_MODEL` still work for the Assistant. You can also set the `PAYARA_AGENTIC_LLM_*` environment variables directly; they win over the file.

### Using a cloud model
- **Assistant:** works with Claude in the cloud: `LLM_BASE_URL=https://api.anthropic.com`, your key and a Claude model name in `llm.env`. The fraud agent shares `LLM_BASE_URL` and `LLM_MODEL`, so for a cloud switch set `PAYARA_AGENTIC_LLM_*` directly for it until its provider keys are known. The client speaks the Anthropic Messages API; other vendors only work through an endpoint with the same API.
- **Fraud agent:** only `provider=ollama` is confirmed. Which other providers Payara's `LargeLanguageModel` supports and which property carries an API key, I could not find in public documentation. Check the Payara documentation or source (`LlmBackendFactory`) for the key names and add them to `META-INF/microprofile-config.properties` or `llm.env` as `PAYARA_AGENTIC_LLM_...` variables.
